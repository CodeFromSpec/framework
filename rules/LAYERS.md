# Layers

How to organize specs into progressive refinement layers. This
document assumes familiarity with
[CODE_FROM_SPEC.md](CODE_FROM_SPEC.md).

---

Specs can be organized into subtrees (layers) within the spec
tree, each adding a domain of specialized knowledge. Layers
enable progressive refinement — a leaf node in one layer
generates an artifact that a leaf node in a subsequent layer
consumes as input.

```
ROOT/domain/           ← business intent (written by non-programmers)
ROOT/functional/       ← pseudocode logic (generated from domain artifacts)
ROOT/implementation/   ← source code (generated from functional artifacts)
```

Within each layer, intermediate nodes provide context and
constraints to the leaf nodes below them. For example, the
intermediate nodes of the `implementation/` layer might prescribe
language, framework, and coding conventions — rules that govern
how the leaf nodes in that same layer generate source code.

---

## How it works

Layers are built on two primitives from the framework:

- **`from`** — a leaf node declares which artifact it consumes
  as input (using an `ARTIFACT/` logical name).
- **`ARTIFACT/`** — a logical name prefix that references a
  generated artifact by node and id.

A layer does not require special configuration. It is simply a
subtree under `code-from-spec/` whose leaf nodes use `from` to
consume artifacts generated by leaf nodes in another subtree.

---

## Example

```
code-from-spec/
├── domain/
│   └── transfers/
│       └── _node.md           ← leaf, artifacts: [{id: default, path: ...}]
├── functional/
│   └── transfers/
│       └── _node.md           ← from: ARTIFACT/domain/transfers
└── implementation/
    └── transfers/
        └── _node.md           ← from: ARTIFACT/functional/transfers
```

The `domain/` layer captures business intent. The `functional/`
layer consumes domain artifacts and produces pseudocode or
detailed logic. The `implementation/` layer consumes functional
artifacts and produces source code.

Within each layer, intermediate nodes define the conventions for
their leaf nodes. Some examples:

- **`ROOT/domain/`** — glossary of business terms, rules for
  writing acceptance criteria, tone and language for
  non-technical contributors.
- **`ROOT/implementation/`** — programming language, framework,
  library versions, error handling patterns, logging
  conventions, project directory structure.
- **`ROOT/database/`** — database engine, schema naming
  conventions, transaction isolation rules, migration format,
  indexing guidelines.
- **`ROOT/external/`** — HTTP endpoints, authentication methods,
  JSON payload schemas, rate limits, retry policies, error
  response formats.
